# Design decisions and open questions

This document records the design gaps found in the [README](../README.md) and how they are resolved.
**Decided** items are the baseline for [ARCHITECTURE.md](ARCHITECTURE.md) and [TODO.md](TODO.md). They can still be
changed, but the change must be made in all three documents. **Open** items need an answer from the project owner
before the phase that depends on them starts.

## Decided (proposed defaults)

| # | Topic | Gap in README | Decision |
| --- | --- | --- | --- |
| D1 | Architecture pattern | Not specified | MVVM with unidirectional data flow. ViewModels expose `StateFlow<UiState>`; repositories are the single source of truth. |
| D2 | Dependency injection | Not specified | Hilt (incl. `HiltWorker` for WorkManager). Pure JVM modules use only `javax.inject` annotations; their Hilt bindings live in Android modules (D25). |
| D3 | Modularisation | Not specified | Multi-module Gradle build (`:app`, `:core:*`, `:feature:*`) with a version catalog and convention plugins in `build-logic/`. `:core:model`, `:core:common`, `:core:data` and `:core:nextcloud` are pure Kotlin/JVM modules (D25). |
| D4 | Navigation | Not specified | Navigation Compose with type-safe routes (kotlinx.serialization). |
| D5 | Grid loading | "Lazy loading" only | Paging 3 backed by Room `PagingSource`. |
| D6 | Index sync | Room *and* MediaStore, but no sync strategy | Full scan on first start, then incremental sync: `GENERATION_MODIFIED` (deletions found by comparing ID sets). Triggered by a debounced `ContentObserver` and on app start. `.nomedia` is respected by MediaStore itself (folders containing it are not in the image collection), so the app does no own `.nomedia` check. Only the folders the user added are read (D55). |
| D7 | Timeline date source | Not specified | `DATE_TAKEN` → EXIF `DateTimeOriginal` → `DATE_MODIFIED`, grouped in the device's local time zone. |
| D8 | Media types | "Images" only | v1 supports images only (JPEG, PNG, WebP, HEIC/HEIF, static GIF). No video. |
| D9 | Viewer zoom / subsampling | "Subsampling" without a library | Telephoto (`zoomable-image-coil`), because it is Compose-native and uses Coil. |
| D10 | Delete and overwrite | README promises trash | Delete uses `createTrashRequest` (undoable); permanent delete via `createDeleteRequest` as a secondary action. Overwriting an original uses `createWriteRequest`. All go through the system confirmation dialog (was O10). |
| D11 | Credential storage | "Keystore-encrypted storage" (`EncryptedSharedPreferences` is deprecated) | DataStore encrypted with Tink AEAD, with the key held in the Android Keystore. |
| D12 | Editor model | Not specified | Non-destructive: a list of `EditOperation` with undo/redo. The preview renders on a downsampled bitmap; saving renders at full resolution. EXIF is copied, orientation is reset to normal and dimensions are updated. |
| D13 | Remote ↔ local mapping | "Relative path" is undefined | Each indexed local folder (D55) maps to `<remoteRoot>/<folder relative path>`. "Uploaded" means the same name and size exist there; checksums only confirm a match when the server provides them. The remote root should match the target folder the Nextcloud app uploads to (D31). Files the Nextcloud app renamed (e.g. on a name conflict) show as "not uploaded"; an optional checksum-only scan of a remote folder is a later option. |
| D14 | Nextcloud accounts | Not specified | One account in v1. |
| D15 | Partial media access | Not mentioned | Support `READ_MEDIA_VISUAL_USER_SELECTED`: show a "limited access" banner with an option to grant more. Added folders (D55) apply on top: an image is shown if it is both selected and in an added folder. |
| D16 | Location redaction | Not mentioned | Use `MediaStore.setRequireOriginal()` when reading EXIF GPS (requires `ACCESS_MEDIA_LOCATION`). |
| D17 | Testing stack | Not specified | JUnit 4, MockK, Turbine, kotlinx-coroutines-test, Robolectric (4.17 or later, the first release with SDK 37 support; needs JDK 21), in-memory Room, OkHttp MockWebServer, Compose UI tests. Behaviour Robolectric cannot reproduce (real MediaStore, Android Keystore, HEIC decoding, system dialogs, map rendering) is tested with instrumented tests (`src/androidTest`). CI runs only JVM tests (plain JUnit and Robolectric); instrumented tests run locally on an API 37 emulator or the Pixel 10a. |
| D18 | Code style / CI | Not specified | ktlint (configured via `.editorconfig`) and detekt; GitHub Actions runs build, unit tests and lint. detekt 2.0 (alpha) is used because detekt 1.23 relies on AGP APIs removed in AGP 9; revisit when detekt 2.0 is stable. |
| D19 | Transport security | Not specified | HTTPS only (cleartext disallowed via `network_security_config.xml`; cleartext allowed in debug builds only). |
| D20 | Tech stack | Listed as "planned" | Confirmed by the project owner: Kotlin, Jetpack Compose (Material 3 components) and Room as the local database. |
| D21 | Target device and SDK levels | "Target the latest SDK" only | Reference device is a **Pixel 10a on Android 17**. `minSdk`, `compileSdk` and `targetSdk` are all 37 (Android 17); older Android versions are not supported. The platform APIs the app needs are therefore always available, so there are no API-level branches. Manual testing and performance acceptance run on the Pixel 10a. |
| D22 | Visual design | Not specified | Delivered by Claude Design: [DESIGN.md](DESIGN.md) (colours, type, shapes, dimensions, wording and states per screen), based on the Cloudsync design system shared with NextAlarm. Task 10.0 applied it to the existing screens before Phase 4; later phases build from it. All colours, typography, shapes and spacing come from `NextGalleryTheme` in `:core:ui`; feature modules never hard-code visual values, so the design can be dropped in without touching features. The launcher icon is delivered: "stacked frames" in the shared Cloudsync colours, with a monochrome layer for themed icons. |
| D23 | Map library and tiles | osmdroid named; tile source not specified (was O2, O3) | OpenStreetMap via osmdroid behind a `MapRenderer` interface (MapLibre stays the fallback if osmdroid causes problems). Default tile source is the OSM tile server with a proper User-Agent; the tile URL is configurable in settings. |
| D24 | Performance targets | "Fast" without numbers (was O14) | 50 000 images on the Pixel 10a: no dropped frames when scrolling or fast-scrolling at the display's refresh rate, warm start under 1 s to the first grid. |
| D25 | Android-independent core | Not specified | Business logic is kept free of Android so most tests run as plain JVM tests on CI. Repositories and all domain logic live in pure Kotlin/JVM modules (`:core:data`, `:core:nextcloud`, `:core:model`, `:core:common`). Android APIs (Room, MediaStore, EXIF, bitmaps, WorkManager, Keystore) sit behind interfaces (ports) declared in `:core:data` and implemented by thin adapter modules (`:core:database`, `:core:media`, `:core:platform`) that only map data. ViewModels use no `android.*` types: routes are passed through Hilt assisted injection, and system dialogs and rendered images cross the boundary as opaque handles (`PlatformConfirmation`, `PreviewImage`). The build enforces the split, because a JVM module cannot depend on an Android library. |
| D26 | Application ID / package name | Placeholder only (was O15) | `net.drehtuer.nextgallery` for the application ID and as package root; modules use `net.drehtuer.nextgallery.<module>` as namespace. |
| D27 | License | "TBD" (was O1) | GNU GPL v3. All dependencies must be GPL-3.0-compatible (Apache-2.0, MIT, BSD and LGPL are fine). |
| D28 | Distribution | Not specified (was O4) | No public distribution for now; the app is built and installed locally. If it is distributed later, it will be through F-Droid, so the build stays free of proprietary dependencies, but F-Droid metadata, reproducible-build tuning and a release pipeline are deferred until then. |
| D29 | Editing formats | Not specified (was O11) | The editor supports JPEG and PNG, and saves in the source format (JPEG quality 95, PNG lossless). Other formats (HEIC/HEIF, WebP, GIF) can be viewed, shared and deleted, but the Edit action is not offered for them in v1. |
| D30 | Editor memory limit | Not specified (was O17) | The app never degrades quality silently and never risks an out-of-memory crash. Before applying a scale and before rendering a full-resolution save (new copy or overwrite), it estimates the memory needed (source and output bitmaps at 4 bytes per pixel) and compares it with the memory currently available. If it does not fit, the operation is refused and the user is told why, e.g. "This image needs about 480 MB of memory, but only 300 MB are available." Bitmap pixels live in native memory, so "available" comes from `ActivityManager.MemoryInfo` (minus a safety margin), not from the Java heap size. |
| D31 | Uploading | Own upload queue was planned (was O5, O6, O7) | The app does not upload by itself. The "Upload" action hands the selected images to the official **Nextcloud Android app** (`com.nextcloud.client`) with an explicit `ACTION_SEND` / `ACTION_SEND_MULTIPLE` intent. The Nextcloud app chooses the target folder and handles name conflicts, large files (chunking), retries and progress. If the Nextcloud app is not installed, the action is disabled with a hint. NextGalleryApp only checks and shows the upload status (badges), refreshed every 6 hours with a network, after a sign-in or a new remote folder, and on returning from the Nextcloud app after a hand-off. |
| D32 | Untrusted server certificates | Not specified (was O9) | System CAs and user-installed CAs are trusted. If the server presents any other certificate (self-signed, unknown CA, hostname mismatch), the app shows a warning dialog with the certificate details (subject, issuer, validity, SHA-256 fingerprint). If the user accepts, the certificate is pinned for that host and trusted from then on; if it later changes, the dialog appears again with a "certificate changed" warning. Accepted certificates can be reviewed and removed in settings. The Login Flow v2 page opens in the browser, which shows its own certificate warning. |
| D33 | Selection across views | Per-screen selection was proposed (was O12) | One app-wide selection of local images. A selected image stays selected when switching between Folders, Timeline and Map, even if the current view cannot show it (e.g. no GPS data on the map, or another folder). The selection bar always shows the total count, and actions apply to the whole selection. A **selection overview** (opened from the selection bar) lists all selected images; images the current view cannot show are greyed out there. The selection lives in memory and is not restored after the process is killed. A virtual folder (D55) can show the images of all its members. |
| D34 | Localisation and colours | Not specified (was O13) | English only; strings are still kept in resources. The colour concept comes from Claude Design (D22). The user picks the accent colour in Appearance from five accents defined by the design (blue, the default, teal, plum, moss, coral), each with its own light and dark values ([DESIGN.md](DESIGN.md)). No dynamic colour. |
| D35 | Logged-out state | Not specified (was O16) | Logout revokes the app password on the server (best effort) and wipes the local credentials, remote listing cache and remote previews. While logged out there is no access to the Nextcloud storage at all: the Nextcloud tab shows a hint that a login is required (with a button to log in), and upload badges and the Upload action are hidden. |
| D36 | Relationship to the Nextcloud app | Not specified | General rule: NextGalleryApp does not offer another way to do something the official Nextcloud Android app already does; it hands off to that app instead (as for uploads, D31). The deliberate exceptions are the built-in remote browser and viewer, because viewing server images inside the gallery is a core feature, and moving and deleting server images (D46). |
| D37 | Remote image caching | Not specified (was O8) | Opened remote originals and previews go into a separate size-limited disk cache for remote images (500 MB, LRU) only. There is no "make available offline" option, because the Nextcloud app already offers one (D36). |
| D38 | Build environment | Not specified | Builds run in a devcontainer (`.devcontainer/`: Temurin JDK 21, Android command-line tools, platform `android-37.0`, AGP's default build-tools). CI builds in the same image via `devcontainers/ci`, so local and CI builds match. Instrumented tests run on the host (emulator or Pixel 10a), not in the container. |
| D39 | Local network access (Android 17) | Found in the platform review (TODO 0.5a) | Apps targeting API 37 cannot open TCP connections to local-network addresses without the runtime permission `ACCESS_LOCAL_NETWORK` (NEARBY_DEVICES group); blocked connections typically time out. Self-hosted servers on the LAN need it. The app declares the permission and requests it when the user starts the Nextcloud login, with a short explanation; if it is denied, connections to LAN addresses fail with a clear error instead of a timeout. How VPN/Tailscale addresses and the browser are treated is not documented and must be tested on the device (Phase 8). |
| D40 | Other platform findings for API 37 | Found in the platform review (TODO 0.5a) | (1) Certificate Transparency is on by default; it is documented as skipped for custom trust anchors in the network security config, but not for a custom `X509TrustManager` – test that accepted self-signed certificates still work (Phase 8). (2) On large screens (sw ≥ 600dp) orientation and resizability restrictions are ignored, so the UI must not lock orientation and must work in landscape. (3) Android 17 enforces per-app memory limits based on device RAM; the editor's memory check (D30) must use the app's real limit, not only the system's free memory – verify on the Pixel 10a (Phase 7). (4) `MediaStore.getVersion()` is opaque and per-app; it is only compared for equality (already the plan). (5) Expedited/regular WorkManager quotas depend on the standby bucket, so the first index may be delayed; the indexing UI should show progress rather than assume an immediate start (not built yet: `IndexWorker` reports no progress, see STATUS.md). (6) Implicit URI grants for `ACTION_SEND` end with Android 18; share intents always set `FLAG_GRANT_READ_URI_PERMISSION` explicitly (already the plan). (7) Native libraries must be 16 KB page aligned; check in Phase 10. Sources: developer.android.com behaviour-change pages for Android 15, 16 and 17. |
| D41 | Code quality reports | Not specified | SonarCloud (project `drehtuer_NextGalleryApp`) shows code issues plus line and branch coverage. CI runs the scan on pull requests and on `main`, because SonarCloud's Automatic Analysis cannot import coverage; it must stay disabled in SonarCloud, or the CI scan fails. Coverage comes from JaCoCo (`./gradlew coverageReport`) and only reflects the JVM and Robolectric tests CI runs, so code covered only by instrumented tests (D17), e.g. `MediaStoreScanner`, shows as uncovered. No minimum coverage is enforced by the build. |
| D42 | App data backup | Not specified | No app data is backed up or moved to a new device: `allowBackup="false"` plus data extraction rules that exclude everything, for device transfer too. The index can be rebuilt from MediaStore, and this keeps credentials (Phase 8) out of backups. The cost is that settings, such as the added folders, virtual folders and the Nextcloud login, must be set up again on a new device. |
| D43 | Timeline scrollbar | "Date-labelled fast scroll" | The timeline's fast scrollbar is a **date rail**: next to the thumb it shows the day in the vertical middle of the screen in a large pill, with the day before and after in small labels (format "24 Oct 2026"). It is drawn above the sticky month headers. The folder grid keeps a plain thumb. |
| D44 | Map viewport | Not specified | The map opens centred on the user's current location at zoom 8. The location comes from the platform `LocationManager` (no Play Services) and needs `ACCESS_COARSE_LOCATION`, asked for the first time the map opens; without it the map opens on the area with the most geotagged images. Zoom is unrestricted within what the tile server offers: 0 (whole globe) to 19 (OpenStreetMap's maximum), and the world repeats horizontally. One finger drags; two fingers pinch to zoom and drag to move; zoom buttons and a "my location" button are always shown. |
| D45 | Place names | Not specified | Photos only carry coordinates, so cluster titles and the location in the details sheet come from an **offline reverse lookup**: the GeoNames list of places with more than 15,000 inhabitants (`cities15000`, CC BY 4.0, roughly 1–2 MB) ships with the app, and the nearest place within 30 km gives "near <town>". A merged cluster is named after its largest place with a town: "near Bolzano and 7 more places". Without a town within 30 km, the cluster shows only its image count and the sheet shows the coordinates. No dates are used, because a cluster mixes dates. Rejected: Android's `Geocoder` (uses Google services, sends locations to Google) and the Nominatim service (online only, sends locations to a third party). The GeoNames attribution is shown in About. The project owner confirmed that the CC BY 4.0 data is fine with the app's GPL licence (D27). |
| D46 | Moving and deleting on the server | Not specified; D31/D36 kept the remote side read-only | The remote browser may **move** images to another server folder (WebDAV `MOVE` with `Overwrite: F`) and **delete** them (WebDAV `DELETE`, which puts them in the Nextcloud trash bin if the server has it on; otherwise see D56). This is a deliberate second exception to D36, requested by the project owner: reorganising server photos must not need a second app. Uploading stays with the Nextcloud app (D31). Name conflicts ask per file: keep both (the moved file gets a " (2)" suffix), replace, or skip, with "do the same for the rest". Undo moves the images back, or restores them from the trash bin (only offered when they went there, D56). Folders where the account lacks write permission (`oc:permissions` without `C`/`K`) are disabled as targets. Moving and deleting need a connection; offline they are disabled with a hint. |
| D47 | Remote context menu and selection | Not specified | In the remote browser a long-press on an image opens a context menu with Move to folder…, Share and Delete (no Properties: the viewer's details cover it). Images are selected with the Select action in the top bar; while a selection exists, a long-press adds that image and the menu acts on the whole selection. The remote selection is separate from the app-wide local selection (D33), lives in memory, and is cleared when leaving the remote browser. |
| D48 | Sharing server images | D47 offers Share, but server images have no local file to share | Share downloads the images to a temporary folder in the app's cache, then opens the normal Android share sheet through a `FileProvider` limited to that folder, with read grants only. The images are not added to the gallery, and the temporary files are removed at the next share and when the app starts. |
| D49 | Long-press in local views (was an open question) | Not specified | In Folders and Timeline a long-press starts the selection, as in Material 3 galleries; the Select action in the top bar does the same. Only the remote browser has a context menu (D47). |
| D50 | Editor tools | DESIGN.md left out Rotate and percentages | The editor keeps all four tools of the README: Rotate, Crop, Scale and Draw. The scale dialog offers a percentage as well as width and height. |
| D51 | Grid columns | DESIGN.md mixed a minimum cell size with a fixed choice | Grids show a fixed number of columns: 3 by default, with 3, 4 or 5 in Appearance. There is no automatic setting. The count also applies in landscape and on large screens, where cells get larger. |
| D52 | Meaning of folder rules (replaced by D55) | Phase 1 treated includes as an allow list (any include hides all other folders), which contradicts the wording in DESIGN.md | "Default shows a folder if it has images. Include always shows it; Exclude always hides it." So the rule nearest to a folder decides (on the folder, else on its closest parent), and an include can open up a subfolder of an excluded folder. A folder without a rule is shown unless it matches an exclude pattern. There is no allow list. The default excludes are ordinary rules, written when settings are first stored, and can be removed. |
| D53 | Showing `.nomedia` folders | DESIGN.md asks for a read-only lock chip on them | The app cannot list them: MediaStore hides their images (D6), the `.nomedia` file itself is not visible through MediaStore, and the app has no all-files access and should not ask for it (the README's minimal permissions). The Folders settings screen says in a note that Android hides these folders. Since D55 the app does not list folders by itself anyway, and if a user adds such a folder, it shows no images. |
| D54 | How the login reaches the browser and notices success | D39 opened the login page in a Custom Tab and polled throughout, ending the login on any network error | The login page opens in the default browser with a plain `ACTION_VIEW`. The app checks at once when it returns to the foreground and every 2 s while there, never in the background, where Android may freeze it and cut its network. Network failures and 5xx answers only postpone to the next check. The login expires 20 minutes after its start. The pending login is kept in `SavedStateHandle`, so a system kill while the user is in the browser does not lose it. |
| D55 | Which folders are shown | D52 showed every folder with images unless a rule hid it, so the app read the whole phone | The owner decides: "Use the android directory picker to add/remove folders. Only added folders are shown." **Added folders:** the user adds folders with the system picker (`ACTION_OPEN_DOCUMENT_TREE`). The picker only chooses a path: no persistable URI permission is taken, and images keep coming from MediaStore with the existing media permissions. A new installation has no folders. Folder rules and exclude patterns are gone with no migration: after an update the app starts without folders and the index empties, as asked for. **Indexing:** an image is indexed if its volume matches, its path is an added folder or below it, and no folder below the added one starts with a dot (this replaces the old default exclude of WhatsApp's `.Statuses`; a dot folder the user added on purpose is shown). `.nomedia` stays with MediaStore (D6). With no added folder on a volume, MediaStore is not queried for it and its rows are deleted. Otherwise the paths go into the query (`RELATIVE_PATH LIKE ? ESCAPE`), for full scans, changes and the ID comparison, and the matcher is the final filter. A change to the added folders runs one debounced full scan. Subfolders show as their own tiles, since tiles are per bucket. **Virtual folders:** any number, each with a name and member folders chosen from the folders that are shown now, stored by bucket id in the settings (no Room change). A member that is not indexed is ignored and comes back if its folder is added again. A virtual folder without images is only listed in Settings. In the folder list they come first, marked with an icon. A copy saved in the editor from a virtual folder opens the real folder. **Limit:** from memory, not checked on a device, Android's picker refuses volume roots, the Download folder itself, `Android/data` and `Android/obb`. Such folders cannot be added; a subfolder of Download can. A choice the app cannot map to a volume and path (a root, another provider) shows a message. |
| D56 | Deleting on a server without trash bin | D46 assumed every server has the trash bin, but it is an app the admin can turn off, and then `DELETE` is permanent and Undo cannot work | The owner decides: ask before a permanent delete. Before deleting, `RemoteFileOperations.isTrashBinEnabled()` reads the OCS capabilities (`ocs/v2.php/cloud/capabilities`): the files_trashbin app reports `capabilities.files.undelete = true` (its `Capabilities.php`, registered only while the app is enabled). **On:** as before, no dialog, Undo restores from the trash bin. **Off or unknown** (not reported, `false`, an unreadable or failed answer, or logged out): a dialog "Delete permanently?" with Cancel (filled) and Delete (in `error`), and after deleting a message without Undo. Unknown is treated as off, the safe side. A known answer is kept in memory per signed-in account (server and user id) until the process ends, so only the first delete waits for it; a failed check is not kept. It is not stored on disk. If the admin changes the setting during a session, the app notices only after a restart. The confirmation is dropped when the account changes. |
| D57 | Licence texts in the app | The About screen lists each library with its version and licence names, but not the full texts; Apache-2.0 asks for a copy of the licence to go with the program | The owner decides that the list is enough: the app does not show or bundle the full licence texts. The generated list stays as it is (task 10.5). |
| D58 | Documentation site | Not specified | `README.md` and `docs/` are published as a GitHub Pages site (https://drehtuer.github.io/NextGalleryApp/) by `.github/workflows/pages.yml`. It runs when a GitHub release is published, so the site describes the latest release rather than `main`; it can also be run by hand. The site is built with GitHub's own Jekyll (`actions/jekyll-build-pages`, theme Primer) from a copy of `README.md` and `docs/`, so the Markdown stays the single source and the repository root holds no site files; the config lives in `.github/pages/`. Mermaid is rendered in the browser with mermaid.js from jsDelivr. The `github-pages` environment must allow deployments from release tags (`v*`). |
| D59 | Dependency updates | Not specified | Dependabot alerts and security updates are on. Version updates (`.github/dependabot.yml`) run weekly for Gradle (version catalog, build-logic, wrapper), the GitHub Actions and the devcontainer base image. Minor and patch updates are grouped into one pull request per ecosystem; major updates come one by one, as they usually need code changes. A new major JDK image is not proposed, because the build needs JDK 21 (D17, D38); the Android SDK versions in the Dockerfile are updated by hand. Gradle dependencies reach the dependency graph through `gradle/actions/dependency-submission`, as GitHub cannot read them from the build files. |
| D60 | Security scanning | Not specified | `.github/workflows/security.yml` runs CodeQL (`security-and-quality` queries) on the Kotlin code and on the workflows for pushes to `main`, pull requests and weekly. The Kotlin build for CodeQL runs on the runner, not in the devcontainer, because CodeQL has to trace the compiler; it uses `assembleDebug` without the build cache, configuration cache and Kotlin daemon, so every file is compiled. Pull requests also get a dependency review that fails on vulnerabilities of moderate severity or higher and on licences GPL-3.0 cannot take (D27). Only dependencies that ship in the app count for it: the submitted graph scopes the `releaseRuntimeClasspath` of the Android modules and the `runtimeClasspath` of the JVM modules as `runtime` (not `:benchmark` or build-logic), and everything else (AGP, lint, detekt, test libraries) as `development`. Dependabot still alerts on development dependencies, but they do not block a pull request: AGP brings libraries with known advisories (for example Bouncy Castle 1.80.2), even in its newest release, and they only run at build time on our own sources; D62 raises them. All actions, GitHub's own included, are pinned to a commit SHA with the version as a comment, and the devcontainer's base image to a digest, as CodeQL and Scorecard ask; Dependabot updates both (D62). `.github/workflows/scorecard.yml` runs OpenSSF Scorecard and publishes its results for the README badge. Code scanning uses this workflow (advanced setup); GitHub's default setup must stay off, or the uploads conflict. Vulnerabilities are reported through GitHub's private vulnerability reporting ([SECURITY.md](SECURITY.md)). Secret scanning with push protection is on. |
| D61 | Releases | D28 deferred a release pipeline until distribution | Releases are published on GitHub, which partly replaces D28: the signed APK can be downloaded there, and F-Droid stays the later option. Pushing a tag `vMAJOR.MINOR.PATCH` runs `.github/workflows/release.yml`. It builds `:app:assembleRelease` in the devcontainer image with `-PversionTag` set to the tag, signs with a key from the `release` environment (secrets `RELEASE_KEYSTORE_BASE64` and `RELEASE_KEYSTORE_PASSWORD`; `RELEASE_KEY_ALIAS` and `RELEASE_KEY_PASSWORD` are optional and default to the keystore's only key and the keystore password; only `v*` tags may use the environment), and verifies the signature with `apksigner`. The repository has immutable releases on, so assets cannot be added after publishing and the tag cannot be moved. The workflow therefore attaches everything to a draft first: `NextGallery-<version>.apk`, R8's `NextGallery-<version>-mapping.txt` and `SHA256SUMS`. The release notes are the version's section in CHANGELOG.md, and the run stops if that section is missing. Publishing is the last step, after which `pages.yml` is called, because a release published with `GITHUB_TOKEN` starts no other workflow. APK names: `NextGallery-<version>.apk` for release (`-unsigned` added without a key), `NextGallery-debug-<version>-<UTC timestamp>.apk` for debug, written to `app/build/outputs/nextgallery/<variant>/` by a task that runs after `assemble<Variant>`. AGP 9 no longer lets a build rename its own output. |
| D62 | Vulnerable build dependencies and code scanning findings | Not specified | The build tools pull in libraries with known vulnerabilities (Bouncy Castle, Guava, jose4j, jdom2, commons-lang3, httpclient, Wire, Logback), and `kotlin-dsl` compiles build-logic with the Kotlin embedded in Gradle (2.4.10, GHSA-r937-wjx7-w2jp). None of them ships in the APK. The settings plugin `nextgallery.dependency-floors` (`build-logic/settings`) raises each of them, wherever it is resolved, to the first fixed version; newer versions are left alone, and modules that must match (bcprov, bcpkix and bcutil; logback-core and logback-classic) share one floor. build-logic uses `org.jetbrains.kotlin.jvm` from the version catalog with the SAM-with-receiver plugin instead of `kotlin-dsl`. Code scanning: CodeQL's `java/local-variable-is-never-read` is excluded in `.github/codeql/codeql-config.yml`, because all its hits are in the `equals()` the Kotlin compiler generates for data objects. The SHA-1/MD5 finding in `ChecksumCalculator` is dismissed: those are the algorithms the server reports in `oc:checksums`, used only to tell whether two copies of the user's own file are the same. Scorecard findings about the repository rather than the code (branch protection, code review, project age, fuzzing, the OpenSSF badge, the Gradle wrapper jar, which `wrapper-validation` checks) are left open. |
